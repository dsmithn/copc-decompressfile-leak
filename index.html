Postmortem · WebAssembly memory

Two missing free() calls

For about a month I was convinced I had a rendering bug. The scene would load on my iPhone, run for four and a half minutes, and then the tab would quietly reload itself. I had two memory instruments running by then, and both of them reported the app was well inside budget. Both were telling the truth. The bytes were in a place neither one could reach.

The symptom

The app is a first-person 3D view that streams LiDAR tiles from USGS as you walk around. Desktop sessions never showed this. On my phone it would get about four and a half minutes in and then the tab would reload, taking the session with it, without raising an exception, an onerror event, or a console message.

I had built two instruments specifically to catch this: one counting GPU bytes, one walking the scene graph and totalling what the renderer was holding. When I finally pulled the kernel log off the device, it showed the tab being killed at 1,574,226 KB — about 1,537 MiB. My scene-graph counter, at that same moment, said 108 MB.

Why nothing could see it

The bytes were in WebAssembly linear memory, which is the decoder's own private heap. Neither instrument could have found them there. The GPU counter only knows about GPU allocations. The scene-graph walker only knows about JavaScript objects the renderer is holding, and a WASM heap is neither of those things.

The obvious fallbacks don't help. performance.memory reports only the JS heap, and WebKit doesn't implement it at all. measureUserAgentSpecificMemory() does count WASM, but it's Chromium-only and requires cross-origin isolation, which makes it unavailable on precisely the browser that was crashing.

I spent a month improving two instruments that were pointed at the wrong address space. Both worked correctly the whole time.

What it actually was

copc.js, the library that decompresses the LiDAR tiles, has two entry points that do nearly the same job. decompressChunk allocates two buffers and frees them both in a finally. decompressFile, about thirty lines below it in the same file, allocates the same two buffers and frees neither. (Both do their allocating before the try, so the sibling has the same structural hole on a throw — it just doesn't leak on the path that succeeds.) 

// decompressChunk — frees both
} finally {
  LazPerf._free(blobPointer)
  LazPerf._free(dataPointer)
  decoder.delete()
}

// decompressFile — frees neither
} finally {
  reader.delete()          ← both pointers leak, every call
}

Each successful call leaves file.byteLength + pointDataRecordLength bytes allocated — the compressed tile, plus one point record. Nothing reclaims them for the life of the LazPerf instance, and instances are long-lived: with no instance supplied, getLazPerf() caches one at module scope, and callers that supply their own generally cache it too.

The proof

I ran the same build on the same phone through the same scripted walk, changing one thing: adding the two _free calls to the existing finally. That is the minimal mobile experiment, not the fuller upstream patch further down. The kill lines below come from the device's syslog over USB, not from anything the page reported about itself.

Build Ran for Outcome
upstream (leaks) 267 s killed — WebContent at 1,537 MB
with the two frees 311 s survived, kernel clean
with the two frees 988 s survived, zero kills of any process

That 267-second death lines up with two earlier recordings of the same crash, at 240 and 263 seconds.

Counting the allocator, not the heap

Reporting heap size would have invited the obvious rebuttal, which is that a growing heap is just an allocator's high-water mark. So the harness counts the two allocations under test directly: bytes requested, minus bytes returned. It sees calls issued from JavaScript, which is where these two live. Allocations made inside the C++ never cross that boundary, and aren't counted. 

real USGS 3DEP tile, 289,466 B — 200 decodes

upstream decompressFile    mallocs 400  frees   0   leaked 57,899,000 B
with the two _free calls   mallocs 400  frees 400   leaked          0 B

per call: 289,495 B leaked vs 289,466 B input
          difference 29 B = pointDataRecordLength, the second malloc

The leak per call is the input buffer plus one point record, landing within 29 bytes of exactly the two allocations. Fragmentation doesn't produce four hundred mallocs and zero frees. The decoded output is byte-identical with the frees added, so nothing about the fix changes what the function returns.

Two hundred decodes of that one fixture leave 57.9 MB unfreed. Scaling it further is arithmetic, not measurement, and it assumes the leak is the only thing consuming the budget: about 7,400 decodes to reach the 2 GiB growth limit Emscripten builds use by default, or 5,400 to reach the ~1.5 GB that ended the session above. That second figure is a zero-baseline number. The 1.5 GB is total process RSS, which the leak contributes to rather than fills on its own, so a real session crosses it sooner.

The same call, in four other projects

Four open-source point-cloud projects call decompressFile. I reproduced the leak in Potree, using its own bundled copy of the library and its own decoder worker with nothing modified: the EPT path it exercises accumulated unreleased allocations, and the COPC path, which routes through the sibling function, did not.

Those two arms decoded different inputs — 5,894 versus 5,089 bytes per call — so treat Potree as confirmation that the leak happens on a real call path, not as a controlled comparison. The controlled comparison is the Node run above. I also stopped the Potree session before it failed, so what it demonstrates is accumulation, not a crash.

The fix

- const blobPointer = LazPerf._malloc(file.byteLength)
- const dataPointer = LazPerf._malloc(pointDataRecordLength)
- const reader = new LazPerf.LASZip()
+ let blobPointer = 0
+ let dataPointer = 0
+ let reader = null
  try {
+   blobPointer = LazPerf._malloc(file.byteLength)
+   dataPointer = LazPerf._malloc(pointDataRecordLength)
+   reader = new LazPerf.LASZip()
    …
  } finally {
-   reader.delete()
+   if (reader) reader.delete()
+   LazPerf._free(blobPointer)   // _free(0) is a no-op
+   LazPerf._free(dataPointer)
  }

Applied to the real copc@0.0.8 and re-run against the exported function, this gives 4000 mallocs, 4000 frees, 0 bytes leaked, with decoded output byte-identical to before.

Moving the allocations inside the try matters more than it looks. In the original they happen before it, so a fix that only adds two _free lines to the finally still leaks the first buffer whenever the second allocation or the constructor throws. Starting both pointers at zero makes that safe, since _free(0) does nothing.

One judgement call in there. The finally destroys the reader before freeing the buffer it was opened on, and the sibling function does it the other way round. Whether the reverse order would touch released memory depends on laz-perf's destructor, which I didn't read. I ordered it conservatively rather than report the sibling as a second bug.

Checking my own work

Before taking any of this to maintainers I ran the write-up through an adversarial review aimed at the measurements rather than the conclusion. It caught four things.

  • A dramatic Cannot enlarge memory … Aborted() crash trace was being presented as this bug's consequence. It came from a broken control arm in the harness. A probe bug, not a finding. Removed.
  • The byte counter credited both test arms with the same input size, though one of them decoded a smaller slice. Wrong denominator.
  • The patch I was about to propose leaked on the constructor-throw path. A bug in the fix itself, caught before anyone else saw it.
  • The claim that the instrument "catches every allocation" was false. Allocations made inside the C++ never cross into JavaScript. Scoped down to what it actually observes.

None of those changed the diagnosis. They changed how much this page is willing to claim.

What this does not show

  • The crash was my application, on my iPhone. Potree was never run to failure; only the leak and its accumulation were measured there.
  • No Potree session was run to a memory ceiling, so the tile-count figures above are arithmetic from the measured per-call leak rather than an observed crash.
  • Three of the four projects were confirmed by reading their source. I did not measure them.
  • Potree's COPC loader holding at zero is a fact about Potree's two loaders, not about the format. loaders.gl and Giro3D both call the leaking function on COPC data.
I root-caused this and fixed it in my own application, where a 988-second run afterwards produced no kill. Nothing has been submitted upstream yet — no issue and no PR, on copc.js or on any of the projects that call it. The Node harness tests copc@0.0.8; the Chrome harness tests an unmodified potree@1.8.0 checkout.
