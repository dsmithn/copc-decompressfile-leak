Postmortem · WebAssembly memory

Two missing free() calls

An iPhone tab kept dying mid-session: no error, no stack trace, and nothing wrong in any memory the page knew how to measure. The bytes were real — they were just somewhere a web app cannot look. The fix was two lines, in a dependency that four open-source point-cloud viewers all call.

The symptom

A first-person 3D view streams LiDAR tiles from USGS. On iPhone it would run for about four and a half minutes and then the tab silently reloaded. No JavaScript error, no onerror, nothing in the page's own memory tracking.

Two instruments had been built to catch exactly this: one counting GPU bytes, one walking the scene graph. At the instant the tab was killed at 1,537 MB, the second was reporting 108 MB.

Why nothing could see it

The leaked memory lived in WebAssembly linear memory — the decoder's private heap. It is not a GPU allocation, so the GPU meter couldn't see it. It is not a JavaScript object, so the scene-graph walker couldn't see it. performance.memory would not have helped either — it reports only the JS heap, and WebKit does not expose it at all. Nor would measureUserAgentSpecificMemory(), which does count WASM but is Chromium-only and needs cross-origin isolation.

Both instruments were correct. They were measuring places the bytes weren't. A month went into refining tools that were pointed at the wrong address space.

What it actually was

copc.js, the library that decompresses LiDAR files, allocates two buffers per call and frees neither. Its sibling function, thirty lines above in the same file, frees both. 

// decompressChunk — frees both
} finally {
  LazPerf._free(blobPointer)
  LazPerf._free(dataPointer)
  decoder.delete()
}

// decompressFile — frees neither
} finally {
  reader.delete()          ← both pointers leak, every call
}

Every decoded tile leaked its compressed size, permanently. The viewer streams many tiles per session, so the leak tracks total bytes decoded.

The proof

Same build, same phone, same scripted walk. The only variable is whether those two _free calls exist. Kill lines come from the device's own syslog, not inferred from the page.

Build Ran for Outcome
upstream (leaks) 267 s killed — WebContent at 1,537 MB
with the two frees 311 s survived, kernel clean
with the two frees 988 s survived, zero kills of any process

The 267-second death matches two earlier recordings of the same crash, at 240 s and 263 s.

Counting the allocator, not the heap

Watching heap size invites the obvious rebuttal — that's just the allocator's high-water mark. So the harness counts the two allocations under test directly: bytes requested minus bytes returned. (It sees calls issued from JavaScript, which is where these two live; allocations made inside the C++ never cross that boundary.) 

real USGS 3DEP tile, 289,466 B — 200 decodes

upstream decompressFile    mallocs 400  frees   0   leaked 57,899,000 B
with the two _free calls   mallocs 400  frees 400   leaked          0 B

per call: 289,495 B leaked vs 289,466 B input
          difference 29 B = pointDataRecordLength, the second malloc

The leak per call is the input buffer plus one point record, to within 29 bytes — exactly the two allocations. Fragmentation does not produce four hundred mallocs and zero frees. The decoded output is byte-identical either way, so the fix changes nothing but the leak.

Two hundred tiles leak 57.9 MB. A viewer panning a dataset loads far more than two hundred. At this tile size that is roughly 7,400 tiles to a 2 GiB WebAssembly ceiling — or about 5,400 to the ~1.5 GB process budget that ended the session above.

The same call, in four other projects

The same call appears in four open-source point-cloud projects. I reproduced the leak in Potree — its own bundled library, its own decoder worker, unmodified — where its EPT loader leaks and its COPC loader, which calls the sibling function, holds at zero. No Potree session was run to failure. Only the leak and its accumulation were measured there; the crash above was my own app.

The fix

  const blobPointer = LazPerf._malloc(file.byteLength)
  const dataPointer = LazPerf._malloc(pointDataRecordLength)
- const reader = new LazPerf.LASZip()
+ let reader = null
  try {
+   reader = new LazPerf.LASZip()
    …
  } finally {
-   reader.delete()
+   if (reader) reader.delete()
+   LazPerf._free(blobPointer)
+   LazPerf._free(dataPointer)
  }

Applied to the real copc@0.0.8 and re-run against the exported function, this gives 4000 mallocs, 4000 frees, 0 bytes leaked, decoded output byte-identical.

Two details the obvious version gets wrong, though. The allocations happen before the try, so if the constructor throws, a naive "just add the frees" still leaks both. And the sibling function frees its buffer before destroying the decoder that was opened on it. Whether that dereferences freed memory depends on laz-perf's destructor, which I did not read — so it is unsafe ordering by construction, not a confirmed bug.

Checking our own work

Before taking this to maintainers, the write-up went through an adversarial review pass aimed at the measurements rather than the conclusion. It found four things worth catching:

  • A dramatic Cannot enlarge memory … Aborted() crash trace was being presented as this bug's consequence. It came from a broken control arm in the harness — a probe bug, not a finding. Removed.
  • The byte counter credited both test arms with the same input size, though one decoded a smaller slice. Wrong denominator.
  • The proposed patch leaked on the constructor-throw path — a bug in the fix itself, caught before it was suggested to anyone.
  • The claim that the instrument "catches every allocation" was false; allocations made inside the C++ never cross into JavaScript. Scoped honestly.

None of it touched the bug itself. What it changed was how much the write-up claimed.

What this does not show

  • The crash was my application, on iPhone. Potree was never run to failure — only the leak and its accumulation were measured there.
  • No Potree session was run to a memory ceiling — the tile-count figures above are arithmetic from the measured per-call leak, not an observed crash.
  • Three of the four projects were confirmed by reading their source, not by measuring them.
  • Potree's COPC loader holding at zero is a fact about Potree's two loaders, not about the format — loaders.gl and Giro3D both call the leaking function on COPC data.
Root-caused and fixed in my own application, deployed, and verified against the original crash. The upstream patch is proposed, not yet accepted. Reproduction harnesses run in Node and in Chrome against copc@0.0.8 and an unmodified potree@1.8.0 checkout.
